屏幕空间利用 + 状态栏显隐：把上下两条空条收回去（v1.6.50）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
零、一句话
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

边到边模式**默认隐藏状态栏**（全屏沉浸，可一键放回来）；关闭边到边时，
顶部不再是一条与页面割裂的主题色空条，底部也不再让出整条导航栏。
全部通过 WindowInsets / View 属性即时生效 —— 不重建 Activity、不重启引擎。

一、先看清"空白"是怎么来的
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

关闭边到边时，旧实现走 `decorFitsSystemWindows = true` + 把系统栏涂成主题底色：

    ┌──────────────┐
    │ 状态栏（纯主题色，什么都没有）│  ← 顶部空条 = 状态栏高度
    ├──────────────┤
    │        页面内容        │
    ├──────────────┤
    │ 导航栏（纯主题色）      │  ← 底部空条 = 导航栏高度（手势 24dp / 三键 48dp）
    └──────────────┘

两条空条都不是"内容需要"，而是**窗口让位后没人去画**。所以修法不是"调小间距"，
而是把这两段交回页面：系统栏透明 + 自己分发 inset。

二、改了哪四处
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Insets.applyWindow：两种模式都 decorFits=false
   · 状态栏/导航栏透明、对比度 scrim 关闭（半透明 scrim 是空条的另一种形态）；
   · 不再有"关闭时涂主题底色"的分支 —— 那条底色本身就是用户眼里的空白；
   · 新增 hideStatusBar 参数：仅当 **边到边 且 偏好隐藏** 时 `hide(statusBars)`，
     并设 `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`（从顶边下滑可临时唤出通知栏）。

2. Insets.applyContent：只剩一条路径
   · 删掉 `if (!edgeToEdge)` 的"还原分支"与 `restoreScrollableBottomPadding`；
   · 它存在的前提是"系统接管内容框"，现在前提没了，留着才是漂移源；
   · 页面底部因此也统一：内容铺到底，可滚动容器靠内容 padding 保证末项滚得出来。

3. MainActivity：底部从"整条导航栏"收到"一道触摸地板"
   `compactBottomFloor(navBottom)`：
   · 手势导航（条高 ≤32dp）→ 只让 8dp（手势区只拦边缘上滑，点击是穿透的）；
   · 三键/两键导航（40dp+）→ 仍整条让开（按键区的点击被系统拿走，控件不能落在底下）。
   实测口径：手势导航底部空条 24dp → 8dp（-67%），三键导航保持不变（安全优先）。

4. MainActivity：顶部优先"还给页面"，页面不配合就回退
   · 灵动岛间距 10dp → 紧凑模式 4dp（App 自己能控的顶部空间就这一段）；
   · 紧凑模式把 WebView 顶到 y=0，页面顶栏通过 `--dsh-safe-top` 吃下让位；
   · 但**页面结构不可预期**：脚本扫不到"贴边且够宽的 fixed/sticky 顶栏"时，
     自动退回原生 topMargin（宁可多一条空条，也不能让标题被状态栏压住）。
     判定依据是脚本完成值里的 `top=N`（实测，不猜 DOM）。

三、状态栏显隐：三条入口，一个合成点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  偏好 key      hide_status_bar，默认 true
  生效条件      MainActivity.statusBarHidden() = 边到边 && 偏好（唯一合成点）
  入口①        灵动岛新按钮 btnStatusBar（图标 + 着色 + 文案三重区分两态）
  入口②        设置 → 外观主题 → 隐藏状态栏（边到边关闭时置灰并说明原因）
  入口③        切回边到边时自动按偏好恢复

为什么紧凑模式不允许隐藏：关掉边到边时用户明确选了"带状态栏"的形态，
那时把状态栏藏起来就是"点了没反应"的另一面。所以按钮在那种模式下直接 GONE。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

一、A：无障碍事件面 —— 把「别人替你干活」的开销关掉（体感最大）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

本应用自带无障碍服务（供 Agent 读**别的** App），这会带来两笔我们没写、但一直在付的代价：

**① 订阅面过宽**：`android:accessibilityEventTypes="typeAllMask"` = 向 system_server
订阅**全设备全类型**事件。`TYPE_WINDOW_CONTENT_CHANGED` 在本应用自己的 WebView 页面里
每秒上百条，每一条都要跨进程派发进本进程，再在 `onAccessibilityEvent`（**主线程**）里
穿过一个 `when` 分支后被丢弃 —— 收进来再扔掉。

改成只订阅 `onAccessibilityEvent` **真正处理的 5 类**：

    typeWindowStateChanged | typeWindowContentChanged | typeNotificationStateChanged
    | typeTouchInteractionStart | typeTouchInteractionEnd

`notificationTimeout` 100 → 200ms：系统侧合并窗口翻倍，派发频率再降一半
（本服务对事件的用途只有「记录最近触摸/窗口/通知」与文本变化摘要，200ms 完全够用）。

**② 自己的聊天页也在建虚拟无障碍节点树**：只要服务开着且声明了
`canRetrieveWindowContent`，**任何** WebView 都会为整棵 DOM 建无障碍节点树。
400 轮会话上千节点，AI 每吐一个 token 就触发一次 DOM 变化 → 遍历 + 序列化 + 派发，
全部记在我们头上。这是「CPU 内存都富余、界面照样卡、profiler 按包名看没有热点」的
典型形态 —— 开销不在我们的代码里。

主 WebView 加 `android:importantForAccessibility="noHideDescendants"`。

**代价说清楚**（写进 XML 注释，免得以后被当成 bug）：
  · Agent 不能再读**本应用聊天界面**的无障碍树 —— 对话内容它本来就在上下文里；
  · **截图不受影响**（`takeScreenshot` 与无障碍树是两条通路），视觉识别照旧；
  · 读**别的 App** 完全不受影响（`scr` 的主战场）；
  · 设置页/扩展中心是独立 Activity，不在此列。
  · 回退：删掉那一行属性即可，其余代码零依赖。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
二、B：引擎 stdout —— 别再用 PTY 把事件循环钉住（只做方案 A）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`dsh_pty.c` 给引擎开的是**真 tty**（`dup2(slave, STDOUT_FILENO)`）。按 Node 文档，
POSIX 下 **TTY 的 `process.stdout` 写是同步的**（文件、pipe 之外唯一的同步情形）：
每条 `console.log` 都要等 tty 缓冲被读走才返回，**期间整个事件循环阻塞**。

tty 缓冲只有几 KB。而旧读端每 4KB 要做：`String(buf, UTF_8)` 解码 → `Log.d`
（一次 logd **跨进程**往返）→ `EngineLog.append(text)` 内部再 `toByteArray()` 编回去。
流式输出时日志最密，读端跟不上 → 缓冲打满 → 引擎 `write()` 阻塞 → WS 不推、HTTP 不应答、
定时器不走，**而 CPU 采样看起来是空的**（它是阻塞，不是计算）。

改法（计划文档的「方案 A」，零 C 改动）：
  · 读块 4KB → **64KB**；
  · **原始字节直落盘**：新增 `EngineLog.appendBytes(file, buf, n)`，配合字节版
    `writeLocked(file, src, off, len)` —— 零解码、零重编码、零 String，环形截断逻辑
    与字符串版**完全一致**（探针里有逐字节等价性对照）；
  · logcat 回显改为 `Log.isLoggable` 门控（默认关；排查时
    `adb shell setprop log.tag.EngineProcess DEBUG`）。

顺带修掉一个潜在乱码：旧实现按 4KB 块**独立**解码，多字节字符恰好跨块时会被解成
替换符 U+FFFD 落进 engine.log；按字节写永远不会有这个问题。

**方案 B（把子进程 stdio 直接接日志文件、彻底不要 tty）本次没有做**，原因诚实写在报告里：
它要新增 JNI + 改启动链路，而「`dsh web: ?token=` 行的解析」和「内核直写绕过 2MB 环形
截断」两点都必须在真机上回归；本环境无设备，做进去等于把「能启动」这个硬前提交给运气。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
三、C：截图 —— 别把 10~20MB 交给 GC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

旧 `screenshotBase64()` 有三处浪费，全是「一张 10~18MB 的图被反复复制」：

  1. `bitmap` **从不 recycle** —— ARGB_8888 整屏 1080p≈10.4MB / 1440p≈18.4MB，
     每截一张就丢一块给 GC；连续截图时堆里同时躺着好几块，抢在分配点上触发 GC；
  2. `baos.toByteArray()` 再把整张 PNG **拷一份**；
  3. 调用方（`AgentBridge.screenshot`）为了 `?max=` 缩放又
     `Base64.decode(b64, ...)` **写了两遍**（一次传数据、一次取 `.size`）→
     两份 2~6MB 数组同时在世，外加上一张全尺寸 PNG 中间态。

改法：
  · 抽出 `capturePng(maxDim, timeout)`：**编码前**缩放（只在真需要缩小时才做第二张图）；
  · base64 用 `android.util.Base64OutputStream` 直接流进 `ByteArrayOutputStream`；
  · 两张 bitmap 在 `finally` 里 recycle（异常路径也不漏）；
  · 新增 `screenshotPngBytes()`：落盘场景（`/shot?save=1`、动作步骤截图）直接写 PNG
    字节，不再「PNG → base64 → 解码回字节 → 写盘」；
  · `AgentBridge` 侧**零解码**：把 `maxDim` 交给截图内部，落盘路径直接拿字节。

四、D：转屏不整页 reload —— 本仓库 v1.5.1 起已实现，本次只补断言
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

计划文档基于 1.4.16，建议「转屏不要整页 reload」。本仓库现状：

  · `onConfigurationChanged` 只做 `applyZoomControls` + `applyEdgeToEdge` +
    `scheduleViewportReapply`（120ms 去抖，**布局完成后**才判渲染模式）；
  · 宽度没变就什么都不做（键盘/insets 只改高度，不会误触发重排）；
  · 模式真变了走 `switchRenderMode` → `verifyModeSwitch`：软切换写 viewport meta，
    再**自校验**（clientWidth、插件让位标记、横向溢出），任一不过才回退整页 reload。

也就是说「转屏 freeze 几秒」在当前版本已不存在。本次**没有改代码**，只新增断言
（`onConfigurationChanged` 函数体内不得出现 `reload()`；reload 只允许出现在
`verifyModeSwitch` 的兜底分支），防止以后有人图省事把 reload 加回来。

**E.1 `NODE_COMPILE_CACHE`**：本仓库 v1.6.x 起已注入（`$DSH_HOME/.cache/node-compile`，
配 flusher 定时落盘，避免强杀丢缓存）。本次补上缺的那一半：**runtime 换版本时清一次**。
缓存键是「路径 + 内容」，旧 runtime 的字节码一个都不会命中，只会白占几十 MB 磁盘，
而用户完全看不出它在做什么。清理刻意做得「宽进严出」：

  · 读不到 `.runtime-version` 时**不清**（宁可留旧缓存，不能因为一次读失败误删有效缓存）；
  · 清理失败只记日志，不阻断启动；目录建不出来时**不设这个变量**（Node 会每条日志刷告警）。

**E.2 `--max-semi-space-size`**：这是**内存换 CPU** 的参数（V8 会预留约 3×N 常驻空间），
4GB 设备盲设 32 完全可能得不偿失。所以做成**设置页开关，默认关**：

  · `EngineV8Flags.nodeFlags(ctx)` 默认返回空列表 = 与旧行为完全一致；
  · 打开后注入 `--max-semi-space-size=16`；
  · 打通了此前「预留但恒为空」的 `EngineProcess.spawn(extraFlags=...)` 接口
    （`EngineSupervisor.spawnEngine` 现在真的传值）。

判断该不该打开的量法写在 `EngineV8Flags` 的 KDoc 里（`--trace-gc` 数 Scavenge）。
**不要和 E.1 一起 A/B** —— 两者都影响冷启动，同时上就分不清谁的功劳。

六、F：桥 —— 请求不再 thread-per-request
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

旧实现每个 HTTP 请求 `Thread(...).start()` 现拉一条线程，而单个请求的活儿并不轻
（截图最长 3s、TTS 播报、落盘数 MB PNG、遍历整棵无障碍树）。动作密集时线程数随并发
线性涨，每条 1MB 栈保留，而真正干活的只有一个核。

改成 **8 条固定线程池 + 有界队列(64) + 满即拒绝（503）**，并允许核心线程超时退出。
为什么必须有界：无界队列在引擎卡住时会一直堆，每个请求都得先等前面那批 5s 超时 ——
「越卡越慢」的正反馈；明确回 503 让调用方立刻退避，比静默排队好得多。

读头也从「逐字节 `read()`」改成 `BufferedInputStream(16KB)`：旧实现一个 500 字节的
请求头 = 500 次系统调用，而桥每秒可能被脚本打十几次（CRLFCRLF 的判定语义不变）。

零、先交代方法：为什么旧结论站不住
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

前几版一直按「渲染不够快」在查：帧预算、Choreographer、合成层、GPU。
这些都**已经是对的**（RenderBudget 单源合帧、5ms 预算、分级降级；
RenderTune 在 document-start 挂载；WebView 渲染进程优先级已提到
RENDERER_PRIORITY_IMPORTANT 且不随不可见让位）。所以继续在这里调参只会
越调越糟。

真正的问题是**顺序错了**：先去量「每帧花了多久」，却没先问「是谁在占着 CPU」。
这次换成**先找异常开销，再谈渲染** —— 具体做法是把所有「跟用户操作无关却在
后台周期性跑」的东西列出来，逐个算它的稳态成本。结论很干脆：

    有一个后台线程每 1.5 秒拉起一个完整的 Node 进程。

这就是「硬件富余却卡」的典型长相：不是算不动，是有东西在**白白烧 CPU**，
而它恰好和用户正在看的页面抢同一批核。

一、根因 1（最重）：TurnWatcher 每 1.5 秒 fork 一个 Node 进程
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`engine/TurnWatcher.kt` 负责「AI 干完活了就弹通知 / 更新灵动岛状态」。它起一条
常驻线程 `while (running) { scan(); sleep(1500) }`。旧 scan() 干两件事：

  ① **遍历整棵 sessions 树**：
       root.walkTopDown().maxDepth(4).filter{ .jsonl / .jsonl.zstd / .json.zstd }
           .sortedByDescending { it.lastModified() }.take(6)
     每一轮对**全部历史会话**做一次 stat，再整体排序。会话越攒越多，轮询越慢 ——
     跟 CPU 快不快完全无关，纯粹是「干了不该干的活」。

  ② **对有变化的 .zstd 会话整体解压**：引擎默认 zstd 落盘，而 zstd 是帧压缩，
     无法按偏移增量读，只能全解。全解的实现是 `ZstdTail.read()` →
     `ProcessBuilder(node, "-e", SCRIPT, file)` —— **拉起一个全新的 Node 进程**：
     实测 40~80MB RSS、上百毫秒启动、还要把几 MB 的会话整个解出来。

关键在于 ② 的去重条件只有 mtime：**用户正在聊天时，会话文件每一秒都在变**。
于是每 1.5 秒就有一次 Node fork，与引擎主进程、WebView 渲染进程抢同一批核。
表现就是「流式输出时界面一顿一顿，但一看 CPU 占用并不高」—— 因为占用是**瞬时
尖峰**，采样看不到，帧却实实在在掉了。

### 修法（四道闸，缺一不可）

1. **目录级缓存**：`sessions/` 的目录列表按它自己的 mtime 缓存；每个项目目录
   内的文件列表按**该目录**的 mtime 缓存（目录 mtime 只在新增/删除会话时变，
   追加内容不会 —— 追加靠 `length()` 发现，两者互补）。稳态成本从
   O(历史会话数) 收敛到「项目目录数 + 候选文件数」个 stat。
2. **静置门槛** 500ms：文件还在写就不解压（解出来是半截，长度判断会错乱）。
3. **全局限流**：两次 Node fork 之间至少隔 **前台 8s / 后台 2s**（读
   `AppForeground`）。用户正盯着屏幕时优先级最低 —— 那时界面自己就会更新。
4. **单飞 + 体积上限**：同一时刻最多一个解压进程，在飞期间直接跳过（**不排队**，
   排队会让 CPU 一直有事做）；超过 32MB 的会话不解压。

### 顺手修掉的一个真 bug

旧代码**先写 stamp 再解压**。于是被限流跳过的那一次，stamp 已经被记成「已处理」
—— 那批内容永久丢失，`turn/end` 静默漏报（通知不来，用户只会觉得「有时候灵
有时候不灵」）。现在改成**判定通过、且解压成功之后**才写 stamp。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
二、根因 2：JSONL 增量解析每轮造 2000+ 个临时对象
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

同一个 scan() 里，增量读也有两处浪费：

  · **双重编解码**：旧实现把整块字节 `String(buf, UTF_8)` 解码，切出完整行后
    再 `complete.toByteArray(UTF_8).size` 把整块**编回去**只为求字节长度。
    同一份数据编解码两遍，每次都是整块新分配。改为在字节数组里从尾部找最后一个
    `'\n'`，偏移直接 `from + end + 1`。
  · **每行三次 substring**：`lineSequence()` + `eventType(line)`（内部
    `indexOf` + 3 次 `substring`）。一段 200KB 增量 ≈ 500 行 ≈ 2000+ 个短命对象，
    每 1.5 秒一次。改为 `countEvents()` 按索引区间扫描，**零分配**：不切行、
    不切子串、不构造 String。

这种事不会出现在任何「卡顿火焰图」的顶部 —— 它不占一次长耗时，它是**持续不断的
小分配**，把 Young GC 频率推高，然后主线程恰好在分配时撞上 GC 暂停。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
三、根因 3：键盘一弹，整页重排 30~60 次
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

`MainActivity.applyIslandInsets()` 里 `wlp.bottomMargin = bottomPad`
（`bottomPad = imeBottom`）。⚠️ 这里**必须**用 bottomMargin 而不是 padding：
只有真正改变 WebView 高度才会触发 `onSizeChanged`，Chromium 才会重排视口
（v1.5.0-beta.6 在 vivo X300 Pro 上的结论，不要"优化"成 padding）。

问题在于：ime insets 在键盘滑入/滑出的 250~300ms 里**每帧都在变**，于是
每帧改一次高度 → 每帧整页重排一次。长对话 DOM 的整页布局是几十毫秒量级，
30 次叠加就是肉眼可见的「键盘一动，页面就卡」。

### 修法

  · **量化到 8dp 台阶**（`quantizeImePad`）：视觉差 ≤8dp（键盘本身一帧就移动
    几十 dp，这点误差看不出来），重排次数从 30+ 降到 4~8 次；
  · **精确收尾**（`scheduleExactImeSettle`）：最后一次 insets 之后 90ms 再补一次
    真实值，保证键盘停稳后底部**不留缝**（单个可取消 Runnable 覆盖式调度，不堆积）；
  · **归零必须精确**：`want == 0` 直接返回 0，收起后不能有残缝。

同一条链上还有两处白费：

  · `FullBleed.updateInsets()` 在 insets 监听器里**无条件**调用（横屏桌面时每帧
    一次），写 4 个 CSS 变量 → 整页样式缓存失效。现在值没变就不注入
    （`sameInsetsCss`，px 级容差）；
  · `logFullBleed(...)` 的字符串拼接写在去重判断**之前**，等于每帧拼一次；
    现在按 `changed` 门控。另外 `findViewById(R.id.statusBarOverlay)` 从监听器
    里提到了外面 —— insets 回调里做 `findViewById` 是一次从根开始的递归树搜索。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
四、根因 4：悬浮窗（灵动岛）一直在**软件渲染**
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

这一条最能解释"明明 GPU 闲着"。

`FLAG_HARDWARE_ACCELERATED` 只对 **Activity 的窗口**由框架自动加。用
`WindowManager.addView` 挂出去的窗口**不会自动带这个标志** ——
缺了它，`ViewRootImpl` 就按软件渲染走：每一帧画到一块 Bitmap 上再上传，
圆角、阴影、半透明全在 CPU 上算。而软件层叠在硬件合成的 WebView 之上，
还会把那一帧变成混合合成路径。

受影响的是所有"addView 挂出去的窗口"：灵动岛、语音面板、手部预览叠层、
工作状态浮窗、桌宠气泡（桌宠主窗和动作菜单当初加了，其余漏了）。
拖动悬浮球、岛展开/收起时 CPU 单核被软件光栅化吃满，卡顿感非常直接。

修法：给这五处 `LayoutParams.flags` 补上 `FLAG_HARDWARE_ACCELERATED`。

五、并发与 IO：两处「生产快于消费、且无背压」
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  · **daemon 状态轮询会排队**（`StatusOverlay`）：原来每 2 秒一次 HTTP GET、
    超时也是 2 秒。引擎一卡（正是要诊断的场景）任务就在单线程池里**排队**，
    越堆越多，之后每个都得先等前面那批超时 —— 形成「越卡越慢」的正反馈。
    现在加单飞闸（`daemonPollGate`，在飞就跳过这轮）+ 间隔 3s；
    顺带把每轮 `new Handler(Looper.getMainLooper())` 换成复用同一个。
  · **日志异步队列无界**（`EngineLog`）：`Executors.newSingleThreadExecutor()`
    的队列是**无界** LinkedBlockingQueue。页面一旦开始刷警告、或磁盘一时忙，
    投递进来的字符串就无限堆在堆里 —— 既涨内存又让消费永远追不上。
    改为 `ArrayBlockingQueue(512)` + `DiscardOldestPolicy`（日志不是业务数据，
    宁可丢最旧的）+ 原子丢弃计数 `EngineLog.dropped`。

六、新增：主线程卡顿归因器（让下一次不靠猜）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

以上四条都是**已经能定位的开销**。但只要还有「硬件富余却卡」的残留，就必须
能在设备上直接问一句「刚才主线程在干什么」，而不是继续换假设。

新增 `ui/MainThreadWatchdog.kt`（仅 debug 包启用，release 零线程零采样）：

    后台线程 post 一个"回执"到主线程 → sleep(400ms) → 检查回执是否按时回来
    没回来 = 主线程此刻被占住 → 立刻读 mainThread.stackTrace

`Thread.stackTrace` 是 JVM 自带快照，不需要任何权限，主线程忙时照样能读。
抓到的栈会归到几个已知热区（BRIDGE / WEBASSET / JSON解析 / 渲染布局 /
SP写入 / 磁盘IO / 锁等待），写进 `engine.log`：

    [main-blocked] 412ms at 磁盘IO
      TurnWatcher.readFrom (TurnWatcher.kt:301)
      ...

三条防「观测反噬」的约束：采样最小间隔 900ms、同签名最多报 3 次、
只在 debug 包启用。它不测帧率（那是 FrameStats 的事），只负责**归因**。

  ① 轮询不再 walkTopDown 整树遍历；候选必须来自目录 mtime 缓存；

  ⑥ CSS 注入与日志必须按 changed 门控；insets 监听器里 findViewById 次数受限；

     `FLAG_HARDWARE_ACCELERATED`；

  ⑨ 归因器的阈值/采样闸/上限/低优先级/debug-only 接线逐项断言。

一、缺陷：开关「只写不读」，拨了等于没拨
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

现场：外观与显示 →「边到边显示（沉浸式）」拨到关闭，界面毫无变化。
原因不是绘制错，而是**这个偏好全工程没有任何一处读它**：

  · `MainActivity.setEdgeToEdgeEnabled()` 老老实实写进 SharedPreferences；
  · `AppearanceActivity` 只在打开设置页时把开关状态回显出来；
  · `ui/Insets.applyWindow()` 无条件 `setDecorFitsSystemWindows(w, false)`
    → 永远是边到边。

代码看起来一切正常（有 switch、有监听、有 setter），测试也全绿 ——
这类"写了没人读"的缺陷只有断言**读取点存在**才抓得住（新增探针见第五节）。

### 修法：把读点下沉到唯一入口，而不是散到 20+ 个 Activity

`ui/Insets` 的两个入口改成**默认参数直接读偏好**：

    fun applyWindow(activity, darkSurface = false,
                    edgeToEdge = MainActivity.edgeToEdgeEnabled(activity))
    fun applyContent(activity,
                    edgeToEdge = MainActivity.edgeToEdgeEnabled(activity))

这样三类调用点全部自动跟随，不需要逐页判断（逐页判断才是下一次漂移的来源）：
  ① `EdgeToEdge` 门面（20+ 处既有调用点）；
  ② `ThemedActivity` 里对 `Insets.applyContent` 的直接调用；
  ③ 以后新写的页面。

### 两种模式到底差在哪

| | 开（边到边） | 关（普通） |
|---|---|---|
| `decorFitsSystemWindows` | false | **true**（内容框退回系统栏之间） |
| 状态栏 / 导航栏颜色 | 透明 | **主题底色 `@color/bg`** |
| 对比度强制（API 29+） | false | **true**（系统按底色决定是否补 scrim，三键导航在浅色主题上才有正确对比） |
| 内容 padding | 由 Insets 按 insets 补 | **摘掉监听器 + 还原原始 padding**（不补，补了就是二次内缩） |
| 灵动岛位置 | `max(状态栏, 挖孔) + 10dp` | **10dp**（内容原点已在状态栏下沿，再叠一次就悬在半空） |
| WebView 底部让位 | IME 高度 | **0**（`adjustResize` 在 fits=true 下恢复生效，自己再加就是双份） |
| 页面 safe-area | 状态栏/挖孔/导航区 | **全 0** |

两种模式下系统栏都**保持可见**：这个开关关掉的是"内容是否画到栏后"，
不是"要不要全屏"。所以随手下滑拉通知栏、返回手势都不受影响。

### 切换是即时的，不需要重启应用

· 设置页拨动 → 当场对**本页**执行 `applyWindow` + `applyContent` + `requestApplyInsets`，
  用户立刻能看到系统栏从透明变成主题底色、内容从栏后退回来；
· 返回主界面 → `onResume` / `onWindowFocusChanged` 各断言一次，
  灵动岛位置、WebView 底部让位、页面 safe-area 一起按新状态重算；
· 每次切换在 engine.log 打一行 `e2e: on/off (islandTop=10dp wvBottom=0dp)`，
  真机上可以直接对上"我点了开关，它到底改了什么"。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. 开关关：状态栏变成主题底色（不再透出壁纸/网页），网页顶部退到状态栏下方，

WebView 渲染调优：合成层预算、离屏跳过、合帧提前到 document-start（v1.6.46）

主题：这一轮**不动观感**，只把"本该由合成器干的"和"不该在主线程干的"分开。
两条硬约束贯穿全文：① 不引入任何全局性的合成层/特效（那是显存爆炸与掉帧的
必然来源）；② 每一条改动都必须可撤销、可观测、默认值与改动前一致。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、合成层：按"意图 + 预算 + 时限"提升，而不是全局开
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. 按下/触摸时，给**最可能要动的那一个元素**挂 `will-change:transform,opacity`，
   让按压反馈的第一帧就在合成器上跑（不然要先建层、丢 1~2 帧）。
2. 预算 3 个、抬手指后 120ms 撤、硬上限 800ms 撤，撤销时**恢复原值**
   （原本是 `will-change:scroll-position` 的，恢复成它，不是清空）。
3. 明确**不做**的三件事（都是经典负优化）：
   · 不给 `*` 或 body 加 `will-change`；不给滚动容器常驻提升（一整屏纹理）；
   · 不用 `transform:translateZ(0)` / `backface-visibility:hidden` 强制提升
     （不可撤销，层数随 DOM 增长）；
   · 不在滚动事件里写任何样式（滚动路径只读）。
4. 所有提升只走 `transform/opacity` 两个合成器友好属性；新增样式规则里
   不出现 `top/left/width/height`。

二、长列表：滚出视口后跳过样式/布局/绘制（仅「流畅优先」档）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Chromium 对 `content-visibility:auto` 的元素在**离屏时**跳过样式、布局、绘制，
这是 CSS 层面的"虚拟列表"，不需要改前端结构。但直接用会踩两个坑：
滚动条跳动（没量过的行按默认高度占位）与"首屏外的输入框被跳过"。

做法：**先量后标**
1. 空闲时（800ms 后、非首屏窗口）限量扫描（≤4000 节点）找出子元素 ≥30 的列表容器；
2. 用 IntersectionObserver（rootMargin 200%，即提前两屏）观察行；
3. 行**第一次进入**视野时，在同一个 rAF 里**先统一读** `getBoundingClientRect`，
   再**统一写** `contain-intrinsic-size:auto <实测高度>` + 类名 ——
   这样离屏后按记忆尺寸占位，滚动条不跳；焦点所在的行永不标记（不丢输入焦点）。
4. 标记数上限 800；`unboost()` 会把类名与行内尺寸全部还原。

默认关闭：只有用户选「流畅优先」才开（有取舍：离屏文本不参与页内查找）。
均衡/画质档下与 v1.6.45 逐像素一致。

三、JS 主线程：把合帧器提前到 document-start（v1.6.37 的真实修复）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

v1.6.37 的合帧脚本是在 `onPageFinished` 注入的 —— 那时页面自己的监听器**早就
注册完了**，包装器只能覆盖"之后"注册的那几个，命中率接近于 0。
v1.6.46 改用 `WebViewCompat.addDocumentStartJavaScript`（androidx.webkit 1.14，
Chromium 83+）在页面任何脚本之前安装，页面从第一行起的 `scroll/resize` 监听
全部经过 rAF 合帧（同一帧只跑最后一次）。内核不支持时静默回退到原路径。

顺带修掉一个**功能性负优化**（v1.6.37 引入）：
`touchmove`/`wheel` 被无差别挪进 rAF，导致监听器里的 `preventDefault()`
在下一帧才执行、此时浏览器已经把手势算成滚动 —— 症状是"弹窗背后的列表能跟着滑"。
现在的规则：`scroll/resize` 总是合帧（不可取消）；`touchmove/wheel/pointermove/
mousemove` **只有确定是被动监听**（显式 `{passive:true}`，或 Chromium 默认被动的
window/document/body 上的 touchmove/wheel）才合帧，其余原样透传。

四、读写分批：我们自己也不许制造强制同步布局
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

第二节的测量严格遵循"一帧内只读一次、只写一次"：先把这一批行的高度全读完，
再统一写类名与尺寸。不做"读一个写一个"（那会让每次写都触发一次强制布局）。

五、观测：把"更流畅了"变成可复现的数字（仅 debug 包）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

新增 `ui/FrameStats`：`Window.addOnFrameMetricsAvailableListener`（回调在独立
线程），只在两个窗口采样 —— **首屏**（onPageStarted → onPageCommitVisible）与
**交叉溶解**（360ms 整屏 alpha）—— 输出：
`frames / p50 / p90 / p99 / jank%(>16.7ms) / layout均值 / draw均值 / sync均值`。
`layout` 与 `draw` 正是验收标准里"单帧 Layout 与 Paint 应趋近 0"的那两项。
release 包不挂载，零成本。

页面侧另有 `PerformanceObserver`（longtask / layout-shift / 慢事件），
加载完成 6s 后由原生取一次快照写 engine.log：`longTasks / longMaxMs / cls / slowEvents`。
两者都不轮询、都是事件驱动。

六、Android 侧：三件"看起来该做、其实不该做"的事
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. **没有**把 WebView 常驻设成 `LAYER_TYPE_HARDWARE`。
   那会把整个 WebView 变成一张离屏纹理：显存按屏幕尺寸乘、视频/Surface 走位、
   输入法弹起时整层重建 —— 是典型负优化。硬件加速本身由系统默认开启
   （`android:hardwareAccelerated` 缺省 true），只在**交叉溶解这 360ms** 内
   临时提升，`withEndAction` 里立刻回 `LAYER_TYPE_NONE`（v1.6.20 起如此）。
2. **保留** `setRendererPriorityPolicy(RENDERER_PRIORITY_IMPORTANT, false)`：
   第二个参数 false = 即使不可见也不降级，这正是防止后台渲染进程被内核冻结的开关。
   它在 `setupWebView()` 内，所以渲染进程崩溃后重建的实例同样生效。
3. **没有**给 JS 桥加"一刀切"的节流：现有桥（`DshAndroidBack.setState`、剪贴板、
   打开/分享）都是导航/用户动作驱动，不是逐帧调用；给它们套节流只会让状态变旧。
   真正高频的是 `evaluateJavascript` 注入：已在 v1.6.20 合并成一次，
   本轮再加两条 —— document-start 已生效时不再重复注入（省一次 IPC）、
   合帧器有 in-flight 守卫（最多一次在飞，其余置 pending）。

设置标题闪烁根治 + 性能流畅度开关 + 内核首屏加载提速（v1.6.45）

主题：三件事其实是同一条线——**"看不见的工作"要么去掉，要么挪到看不见的时候做**。
闪烁是"浮层压在运动内容上"的必然结果；性能开关是把已经在跑的策略交还用户；
内核提速是把首帧窗口里的 IPC/IO 挪到窗口之外。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
一、「设置」标题闪烁残留 —— 根因与重做
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

一.1 根因（两条，都是结构性的，调参数救不了）
1. **34sp 大标题是浮在 ScrollView 之上的浮层，底衬只有 62dp。**
   标题实际占据 60~100dp，即 62~100dp 那一段**没有任何遮挡**。列表行滚过时
   就从「设」「置」两字的笔画缝隙与字腔里穿过去；字是抗锯齿的半透明边缘，
   压在逐帧变化的内容上 → 看到的就是"字在闪、后面有东西在动"。
   只要滚动就必然发生，与机型无关。
2. **每帧对文字做连续缩放**（`scaleX/scaleY = 1 - 0.4375*t`）。
   TextView 的缩放不是位图缩放：canvas 会按新比例**重新栅格化字形**
   （hinting、灰度抗锯齿全部重算）。比例每帧变 → 每帧重算 →
   字形边缘持续抖动，同时每帧一次 invalidate。

一.2 做法：把「移动的字」移出浮层（重做组件）
1. **大标题回到滚动内容里**，成为普通内容节点。它随内容上移、被 ScrollView
   在 y=0 处**硬边裁剪**、再被不透明标题条盖住 —— 全程不存在"浮层压在运动
   内容上"的时刻。裁剪是硬边，不是 alpha 合成，不可能有残影。
2. **新增 `ui/CollapsingTitleBar`**：只是一个不透明窄条（62dp），里面只放一个
   20sp 小标题，小标题上下各留 19dp，完全落在自己的底衬内。
3. **大小标题只做 alpha 交叉淡化 + 4dp 平移，绝不 scale**。alpha 是合成器操作、
   translation 是矩阵平移，两者都不触发文字重新栅格化 → 零字形抖动。
4. **`setProgress` 是纯函数**：区间外自动钳制，重复/反向/跳变调用都收敛到同一
   结果。没有状态机，也就不需要任何 postDelayed 去"还原"。变化 < 0.4% 时
   直接跳过写入（滚动回调每帧都进来）。
5. **顺带修掉三处滚动路径浪费**：
   · `applyHeaderTransform` 不再每帧两次 `findViewById`（改缓存引用）；
   · 搜索开合的 `titleFlight` 不再复制"收起轨迹"的缩放（那等于开合期间再连续
     重栅格化 420ms 字形，就是"打开搜索时标题明显抖一下"的来源）；
   · 折叠停靠点重新推导：完全收起 = 搜索栏顶边(125) − 标题条(62) = 63dp
     （旧值 115 是给浮层缩放那套用的，会让内容多滚 52dp 空白）。

一.3 效果对照
| | 改动前 | 改动后 |
|---|---|---|
| 62~100dp 区域 | 列表行从字腔里穿过 | 不透明标题条完全遮挡 |
| 标题缩放 | 每帧重栅格化字形 | 无缩放（alpha 交叉淡化） |
| 滚动回调 | 2 次 findViewById + 4 次属性写 | 0 次 find + 2 次 alpha 写 |
| 收起后多滚 | 至 115dp | 至 63dp（齐平标题条下沿） |

二、设置新增「性能与流畅度」四项（都是把已有策略交还用户）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

设计前提：**默认值与改动前完全一致**，不选任何东西的用户行为不变。

1. 界面动效（完整 / 精简 / 关闭）—— `PerfPrefs.MotionLevel`
   · 完整：滑入 + 保持（原行为）
   · 精简：纯淡入淡出（新增 anim/page_fade_in|out），去掉最贵的整屏位移合成
   · 关闭：`overridePendingTransition(0,0)` 瞬切；头部吸附与标题淡出同步瞬切
   · 接线：ThemedActivity 每次导航读当前档位 → 改完立刻生效，不需重启

2. 内核渲染档位（流畅优先 / 均衡 / 画质优先）—— `PerfPrefs.RenderProfile`
   · 流畅优先：**始终**注入降级样式（卸 backdrop-filter/模糊/多层阴影/will-change）
   · 均衡：只在系统报告热受限时降级（v1.6.36 原行为）
   · 画质优先：**永不**降级，宁可发烫也保留观感
   · 关键设计：热状态只是**输入之一**，与档位在 `ThermalRenderGuard.resolve`
     里统一合成 —— 避免两处各自算一遍导致来回抖

     实例退役时撤销登记，不会打到已销毁对象

三.1 首屏静态资源「热清单」预载（WebAssetCache）
问题：内存层每次启动都是空的。第一次导航时每个 CSS/字体都要走 stat + readBytes
（或 mmap），而这几百 KB 恰好落在首屏最拥挤的时间窗里。v1.6.25 的预热只在
**首帧之后**才落盘 —— 它只让"第二次启动"变快，"本次启动的首屏"始终是冷的。

做法：
· 学习结束后把渲染阻塞类资源（CSS / woff2 / woff / ttf / otf）按 URL 记进
  `hot.txt`；
· 下次启动在 IO 线程上按清单预读进**内存层**（单条 ≤512KB，总量 ≤4MB，
  最多 48 条）；
· stamp（版本/引擎运行时）变了就删掉热清单 —— 否则全是死 key；
· 容量修剪不会误删 hot.txt。
· **刻意不收 JS**：拦截 JS 会脱离 Chromium 的 HTTP cache 与 V8 code cache，
  每次导航重新 parse+compile，对 1MB 级 SPA 是几十上百毫秒的倒退（v1.6.25 的
  结论，这里继续遵守）。

三.2 首帧后收尾移出淡入窗口（MainActivity）
`onPageFinished` 里原本同步跑四项维护工作：装预览守护、清预览历史、重注降级样式、
装高频事件合帧脚本。而那正是**遮罩淡出 + WebUI 淡入（360ms 整屏 alpha 合成）**
的时间窗。这四项与"这一帧能不能画出来"无关，现统一挪到 `postDelayed(400ms)`，
并带实例守卫（页面已换/已销毁就跳过）。
保留同步的只有两项：`dropPreheatHistory`（用户可能立刻按返回，历史栈必须一致）
与桥接注入（功能）。

横屏真正铺满全屏：移除四边留白 + 视口 1:1 + 页面内解除窄容器（v1.6.43）

主题：v1.6.42 把「让位（避开灵动岛/系统栏）」做在了 WebView 外面 —— 给 WebView 加了
四边 margin。WebView 一缩，露出来的是 Activity 的 windowBackground，于是横屏变成
「上下左右各一条空白/黑边」。让位本身没错，错的是**让它缩小了容器**。

一、根因（三条，都在 v1.6.42 引入）
1. **四边 margin**：横屏桌面下 topMargin=岛带高(≈44dp)、marginStart/End=挖孔/系统栏、
   bottomMargin=导航条。四条全非 0 → 页面只画在中间那块里，四周全是窗口底色。
2. **伪造宽布局 + 缩小**：桌面视口写 `width=max(1024, 窗口CSS宽)`、`initial-scale=
   窗口宽/布局宽`。手机横屏 851dp → 0.831 倍，1 CSS px < 1 设备 px，整页连同四周
   一起变小；再叠加页面自己的 `max-width` 容器，就是"居中窄栏 + 左右大片空白"。
3. **页面自身的窄容器从未被解除**：桌面 UI 普遍 `max-width: 1280px; margin: 0 auto`，
   窗口不够宽时它自己就居中留边 —— App 侧此前完全没处理这一层。

二、改法
1. **容器满幅、让位搬进页面**（`app/src/main/assets/js/full-bleed.js` + `web/FullBleed.kt`）：
   - WebView 四边 margin 恒为 0，保留的只有「底部让 IME」（v1.5.0-beta.6 的真实修复，
     键盘浮在窗口之上必须缩）；
   - 安全区改为 CSS 变量 `--dsh-safe-{top,left,right,bottom}` 注入页面，样式表只给
     **页面自己的 fixed/sticky 顶栏/底栏**加 padding —— 滚动内容仍然延伸到屏幕边缘，
     这才是 Edge-to-Edge 的沉浸感（而不是把整页缩进安全区）。
   - 同时解除外壳容器的 `max-width` / 居中 margin / `aspect-ratio`，让内容吃满 100%。
     扫描限定在 body 起的 3 层内、跳过 `fixed/absolute`、`role=dialog|menu|tooltip`、
     `aria-modal`，且只处理宽度 < 视口 96% 的容器 —— 弹窗、浮层、下拉菜单绝不被动。
2. **视口 1:1 零缩放**：`width=device-width, initial-scale=1.0, maximum-scale=1.0,
   user-scalable=no, viewport-fit=cover`。布局宽 = 窗口 CSS 宽，页面拿到的 100vw
   与屏幕完全一致；「桌面宽布局」由上面的外壳解除来实现，不再靠缩放制造宽度。
   删除 `desktopLayoutWidth()` / `DESKTOP_MIN_LAYOUT_PX` / `DESKTOP_MAX_LAYOUT_PX`。
3. **自愈校验加第三道**：软切换后 380ms 读回 `clientWidth`（±2%）、手机 UI 插件标记、

横屏桌面布局自适应 + 沉浸式安全区 + 转屏不闪烁（v1.6.42）

主题：横屏切桌面端布局这条链本来就有，但三个环节各自是坏的 —— 桌面视口写死 1280
导致手机上字号只剩六成半；灵动岛浮在网页上把桌面 UI 自己的顶栏压住；转屏走整页
reload，一次转屏一次白闪 + 对话滚动位置归零。

一、根因（三条，逐条独立）
1. 桌面视口固定 `width=1280` + `initial-scale=窗口宽/1280`：
   · 手机横屏 851dp → 缩放 0.665，14px 字号只剩 9.3px，点不动；
   · 平板 1137dp → 0.888，白缩一圈；
   · 大屏 1600dp → **1.25 倍放大**，一屏看不到全貌。
2. 横屏没有任何让位：WebView 是 match_parent 全屏垫底，灵动岛（44dp 工具栏）
   浮在顶部，桌面 UI 自己的顶栏/第一行正好被压住；底部横屏手势条压住最后一行。
3. `scheduleViewportReapply` 判出模式变化就 `reload()`：布局本身并不由 UA 决定
   （手机 UI 是引擎侧客户端插件按视口宽判定），整页重载纯属多余代价。

二、改动
1. **桌面布局宽自适应**（`desktopLayoutWidth`）：`max(1024, cw)` ——
   · 永远 ≥ 1024（常见桌面断点，且远高于 narrow 插件「横屏不接管」的 900px 阈值）；
   · 永远不放大（旧实现在 1600dp 上是 1.25 倍）；
   · 窗口中 1024–1280 区间与更宽屏都是 **1:1 零缩放**，字最清晰。
2. **横屏沉浸让位**（只对「桌面渲染 + 屏幕横屏」生效，竖屏逐项为 0）：
   · 顶部让开 `状态栏/挖孔 + 10dp + 灵动岛展开态 44dp`；
   · 左右让开「挖孔 ∪ 系统栏」并集（横屏三键条可能贴边）；
   · 底部让开 `max(IME, 导航条)`（键盘优先，IME 高度已含导航区）。
   为什么用 **margin 而不是往页面注入 CSS padding**：桌面 UI 多为 `height:100vh`
   固定视口布局，给 body 加 padding 不会缩小 100vh，底部会溢出被裁；而 App 侧
   也无从知道引擎那套 DOM 的根节点叫什么（升级即变）。margin 让 WebView 视图
   真的变矮/变窄 → `onSizeChanged` 必然发生 → Chromium 按新尺寸重排，`100vh`
   自动正确。与 v1.5.0-beta.6 修 IME 时选 bottomMargin 是同一个理由。
   顶部带高固定按**展开态**预留：收起成小圆点时那条仍是主题色留白，换来的是
   「点岛不重排」—— 若按当前状态实时算，每点一次岛都要整页重排一次。
3. **软切换 + 双道自校验 + 兜底**（`switchRenderMode` / `verifyModeSwitch`）：
   切模式不再 reload，而是改 UA（settings 层 + 当前文档 `navigator.userAgent`
   即时覆盖，可逆）、改缩放手势、立刻写新视口 meta、重排 insets；380ms 后校验：
   ① `documentElement.clientWidth` 是否等于刚写的布局宽（±2%）；
   ② 手机 UI 插件是否已让位（`data-android-narrow-sidebar-col` / `-yield-col`
      仍在 = 没跟上宽度变化）。两道都过 → **零重载**；任一不过 → 回退成旧的整页
   reload（不退化）。校验用 token 作废旧回调，快速来回转屏只认最后一次。
4. 顺带：改「页面缩放」不再整页 reload（重写 meta 即可）；settings 里换朝向
   返回主界面时，UA / 视口 / 让位边距一并重算，不再只对齐一半。
5. `viewport-fit=cover` 两个视口构建器都保留/补齐，配合已有的 `--dsh-safe-*`
   CSS 变量，页面想自己绘制到系统栏后方时也能拿到四边数值。

三、竖屏
**逐项保持原样**：topMargin 恒 0（v1.4.63 的全屏决定）、左右让位 0、底部只让 IME、
竖屏视口仍是 `width=窗口CSS宽/R` + 锁定缩放（user-scalable=no）。探针里对这几条
逐项断言，防止以后再被"顺手统一"掉。

    逐条断言 `scale <= 1`、`布局宽 >= 1024`；旧写死常量与 "var W=1280" 必须已消失；

设置全局深度搜索：跨一到四级页面检索 + 精准落位 + 状态保持（v1.6.41）

1. 索引是**运行时扫布局**：v1.6.38 只遍历主页 columnPrimary/columnSecondary 里的

   语音服务 + 语音输入 + 宠物 + 台词 + 插件市场 + 扩展中心 + 数据备份 + 维护 +

Linux 伪装模式下搜索工具不可用修复（v1.6.40）

主题：开启 Linux 环境伪装后，grep/rg 工具全线报 "ripgrep launch failed"；关闭后正常。

一、根因（用真实 @vscode/ripgrep 1.18.0 + 真 node 复现）
@vscode/ripgrep 的解析只有三行（lib/index.js）：
    const arch = process.env.npm_config_arch || process.arch;
    const platformPkg = `@vscode/ripgrep-${process.platform}-${arch}`;
    resolved = require.resolve(`${platformPkg}/bin/rg`);
伪装层把 process.platform 改成了 'linux'（FakeLinuxEnv 的 preload），于是它去找
@vscode/ripgrep-linux-arm64；而运行时实际装的是 @vscode/ripgrep-android-arm64
（这个名字在 npm 上 404 —— 是本工程按 ABI 重打包的）。require.resolve 抛
"Could not find @vscode/ripgrep-linux-arm64" → 工具层只看到 ripgrep launch failed。

二、为什么不能手工改 node_modules、也不能换 Linux 二进制
- node_modules 里的任何手改，都会在 App 升级 / 运行时重装 / 自检覆盖时被冲掉；
  修复必须落在 App 侧的自愈流程里，每次引擎启动重新确认。
- 底层仍是 bionic/Android，真 Linux 版 rg 是 glibc 链接，根本起不来。
  所以只补「名字解析」这一环，别名里放的**仍是 Android 原生那一份**。

三、实现（新增 app.dsh.mobile.engine.RgPlatformAlias）
1. 名字映射：ripgrep-android-<arch> → ripgrep-linux-<arch>（只做这一种，别的不猜）。
2. 别名位置：建在「真实包的同一级目录」，而不是写死某个 node_modules。
   这样 hoisted（lib/node_modules/@vscode）与 pnpm
   （.pnpm/@vscode+ripgrep@x/node_modules/@vscode）两种布局都自动正确 ——
   pnpm 下 require.resolve 是从**真实路径**往上找的，那里才是必须命中别名的位置。
3. 材料化：优先软链（绝对路径，整树搬家不失效），失败则整包复制并把
   package.json 的 name 改成别名；复制后内容仍与 Android 原生一致。
4. 体检与重建：别名悬空 / 指错 / 半截（缺 package.json 或 bin/rg）一律重建；
   完好则 KEPT，不重复搬运（幂等）。
5. 接入 NativeLinkFix.heal 的顺序：补库 → 包名对齐 → 包包装脚本。
   只有 Linux 伪装开启时才**新建**别名（原生模式不制造多余包）；
   已存在的别名无论开关都会被体检修复，避免用户关了又开时拿到坏别名。
6. 包装脚本候选按真实路径去重并优先非软链写法，避免每次启动在两种路径
   拼写之间来回改写。

四、验证（scripts/probes/_test_rg_linkfix.py，80 项全绿；含真实 node 端到端）

搜索工具 rg 动态链接库修复（v1.6.39）

主题：工具调用 rg 报 CANNOT LINK EXECUTABLE "rg": library "libpcre2-8.so" not found，
而同一台设备的 bash 里 rg 正常 —— 搜索功能整体不可用。

一、根因（三方对照实测得出，不是推测）
1. 搜索工具**不走 PATH**：它拿 @vscode/ripgrep 导出的绝对路径直接 spawn
   （node_modules/@vscode/ripgrep-android-arm64/bin/rg）。
2. 该二进制是 Termux 官方构建的动态链接 ELF（ripgrep 15.2.0），实测：
     DT_RUNPATH = /data/data/com.termux/files/usr/lib   ← 目标机不存在，等于没有
     DT_NEEDED  = libpcre2-8.so, libdl.so, libc.so
   RUNPATH 不含 $ORIGIN、也不是本工程路径 → libpcre2-8.so 只能靠 LD_LIBRARY_PATH
   或 linker 默认搜索目录命中。
3. 只要子进程环境里没有 LD_LIBRARY_PATH，bionic 立刻报上述错误；bash 里能跑正是
   因为 Termux 布局的 shell 注入了库路径。根模式的 su 包装**会清空** LD_LIBRARY_PATH，
   而旧实现只补了 HOME/PATH/DSH_HOME —— 这是最典型的「终端正常、搜索报错」场景。

二、三层修复（对应三种方案，互为兜底，均幂等）
① 环境注入（首选，惠及所有原生工具）
   · EngineConfig 新增 nativeLibDirs/nativeLibPath 作为**唯一真源**：
     engine/lib → engine/usr/lib → 各扩展 lib → **APK nativeLibraryDir** → 宿主继承值。
   · buildEnv 的 LD_LIBRARY_PATH 直接取它（不再有第二份拼装代码）。
   · EngineProcess 的两个 su 分支（原生 / Linux 容器）补 export LD_LIBRARY_PATH：
     su 出于安全会清空该变量，这是旧实现的致命遗漏。
② jniLibs 打包（长期规范）
   · app/src/main/jniLibs/{arm64-v8a,x86_64}/libpcre2-8.so（Termux pcre2 10.49，
     SONAME=libpcre2-8.so，仅依赖 libc.so，ABI 与运行时同源）。
   · packaging.jniLibs.useLegacyPackaging = true：AGP 8 默认不把 .so 解压到盘上
     （只在 APK 里由 linker 映射），而 execve 起的孙进程只能走真实文件路径，
     不开这个开关等于白放。keepDebugSymbols 保护第三方预编译库不被 strip。
③ 包装脚本（Workaround 兜底，工具层环境不可控时唯一有效）
   · NativeLinkFix（引擎启动时调用，幂等）：
     - 缺库时从 nativeLibraryDir 往 engine/lib 补一份（运行时 zip 漏打包也能活）；
     - 把 rg 真二进制就地改名为 rg.real，原位置写 sh 包装脚本，
       export LD_LIBRARY_PATH 后 exec 真二进制（同名替换，绝非 PATH 前置）。
   · 模板抽到 RgWrapperScript（纯函数、无 Android 依赖，便于离线端到端验证）：
     #!/system/bin/sh、保留已有 LD_LIBRARY_PATH 追加在后、exec "$@" 保证
     stdin/stdout/退出码/信号语义与真二进制完全一致、真二进制缺失时 127 报错
     且不递归回退（避免无限套娃）。

三、验证（scripts/probes/_test_rg_linkfix.py，44 项全绿）
· 修复前复现：用 gcc 造一个复刻 rg 处境的二进制（NEEDED 指向只在私有目录的库、
  RUNPATH 抄 Termux 失效路径），干净环境 spawn 必定失败：
    error while loading shared libraries: ... cannot open shared object file
· 修复后：包装脚本 exit=0，输出 ripgrep 15.2.0，stderr 为空，参数（含空格）完整透传，
  已有 LD_LIBRARY_PATH 时追加而不覆盖，真二进制缺失时确定性 127。
· 另用真实 ripgrep 15.2.0 二进制驱动同一份包装脚本：rg --version 输出
  "ripgrep 15.2.0 (rev e89fff89ac)"，rg -n 搜索目标 <dir> 正确命中文件与行号。
· 打包侧：APK 内 lib/arm64-v8a/libpcre2-8.so 取出后 SONAME/架构/NEEDED 与源文件一致
  （未被 strip），AndroidManifest extractNativeLibs=true。

四、不动的东西
· 引擎/工具代码零改动：dsh-tool-fs-search 的 resolveRgPath、@vscode/ripgrep 的解析
  逻辑都不碰，改的全部在 App 侧与打包配置。
· bash 工具链不受影响：包装脚本只在 LD_LIBRARY_PATH 缺失时才起作用；
  正常注入时行为与原来完全一致（多一层 exec，无额外输出）。

设置搜索修复与取消态重构（v1.6.38）

主题：搜索打不开/筛不出 + 取消后「设置」大字与首页栏残留在列表上——同一组状态缺陷
的两个症状。按 settings-preview.html 的结构重构，从根上消除这类残留。

一、根因（旧实现三处结构性问题）
1. 首页搜索栏被放在 ScrollView **外面**（固定悬浮兄弟节点，marginTop=125dp），
   再用手写的 scaleY + 子 View alpha 模拟「随滚动收缩」。这份视觉状态只能靠
   closeSearch 的 postDelayed 回调还原 —— 回调一旦丢失（重入/转屏/退后台/
   提前 return），alpha 与 scale 就永久停在中间值，于是它带着放大镜和麦克风
   图标残在列表上方。
2. openSearch/closeSearch 都是「先改 searchOpen，再 findViewById(...) ?: return」。
   取不到 overlay / input 时函数提前返回，但状态已经翻了：searchOpen 卡在 true
   → 之后再点搜索入口被 `if (searchOpen) return` 吃掉（这就是「搜索无法正常使用」）；
   而 titleFlight(true) 已经把标题 alpha 打成 0，没有任何人负责写回。
3. applyHeaderTransform 只写 scale/translationY，**从不写 alpha**。
   标题的 alpha 一旦被搜索动画改成 0 就再也没人恢复。

二、重构
1. 搜索入口移进滚动内容（与 preview 的 .search 一致）：滚动时它天然随内容走，
   收缩只是几何变换，**没有任何需要恢复的状态**，从结构上不可能再压到列表上。
   顶部留白同步由 184dp 改为 125dp；searchSettings 由不可聚焦 EditText 换成
   TextView（纯入口），整行 + 语音键都可点开搜索。
2. 头部外观改为 scrollY 的**纯函数**：applyHeaderTransform 每次把
   scaleX/scaleY/translationY **以及 alpha=1** 一次写全。任何一次调用之后
   头部必然处于完整自洽状态，不存在"半截"。
3. 标题飞行（titleFlight）与滚动渲染永不重叠：飞行期间滚动监听直接跳过；
   飞行 onEnd 才把头部交回 applyHeaderTransform；resetSearchUi 也不再抢飞行中的动画。
4. 收尾只有一个入口 resetSearchUi()（幂等）：可见性/alpha/输入/结果/标题/首页栏
   一次全部落到确定值。触发点 = 淡出 animator 的 withEndAction + 260ms 兜底延时
   + onDestroy。先取控件再改值，任何一步为空都不留中间态。
5. 打开时搜索框从首页栏的屏幕位置起飞（对应 preview 的 --bar-dy）：先 post 布局
   再量 getLocationInWindow，不依赖写死的 60/62/125 常量，也不受状态栏 inset 影响。
6. 返回键 = 取消搜索（对齐 preview 的 Esc），而不是直接退出设置页。

三、搜索逻辑
1. 进页面时建一次索引（不再每次输入现场递归读卡片），标题 + 说明 + 人工别名三级匹配。
2. 排序：标题前缀命中 > 标题包含 > 说明/别名命中，同档保持原阅读顺序。
   别名补齐用户实际会用的词：局域网/悬浮窗/语音/权限/深色/代理/Linux 等。
3. 建议 chips 由 3 个扩到 5 个（加「局域网访问 WebUI」「悬浮窗状态显示」）。
4. 结果行：标题命中片段高亮 + 说明两行省略 + chevron；点击 → 关闭搜索并平滑滚到该行；
   回车 = 跳第一条结果；无结果给出带关键词的空态。
5. 每次新查询把结果列表滚回顶部；清除按钮只在有输入时出现。

四、验证
- 逻辑侧：本机复刻排序算法跑了 15 组查询，前缀/包含/别名三档次序正确，
  无结果查询返回空态（显示→外观与显示+悬浮窗状态显示；深色/别名→外观与显示；
  局域网→局域网访问 WebUI；插件→插件快速启动在前）。
- 结构侧：aapt dump xmltree 确认 homeSearchBar 已是 settingsContentWidth 的子节点，
  固定层只剩 62dp 底色 + settingsTitle + searchOverlay 三者。
- 真机侧（本环境无设备，留给验收）：
  · 点搜索入口 → 面板淡入、搜索框从首页栏位置飞上顶部、标题沿滚动轨迹收起；
  · 输入「显示」→ 立即出结果；
  · 点取消 → 面板消失，标题与首页栏回到"从没进过搜索"的样子（无大字压列表、无图标残留）；

渲染进程回收自愈与异步启动（v1.6.37）

主题：修掉 ColorOS 后台回收渲染器引发的「重载死循环」，把 WebView 初始化挪到后台线程，
并对高频事件做宿主侧合帧。

一、渲染进程死亡 → 静默恢复（第一优先级）
- 旧行为：onRenderProcessGone 里当场 recoverWebView()（remove + new + loadUrl）。
  ColorOS 后台回收渲染进程 → 立刻重建并加载 → 再次被回收 → 再重建 …… 死循环，
  期间遮罩/白屏反复闪出，日志里能看到几十条 recovered。
- 新行为：onRenderProcessGone 只做「退役」——retireDeadWebView()：
  ① 先置 webViewDead = true（此后所有入口拿到 null）；
  ② parent.removeView(旧实例)；
  ③ destroy()；
  ④ pendingRecovery = true；
  ⑤ return true（告诉系统已处理，别杀 App）。
  不弹窗、不 reload、不碰引擎。
- 恢复时机严格限定在前台：onResume 里 if (pendingRecovery) → recoverWebViewSilently()。
  新建实例 → 重新 setupWebView() → 复位返回栈/预热/导航态 → 静默 loadUrl → 淡入 120ms。
- 严格约束落地：新增 liveWebView()（已退役或未初始化返回 null），
  onResume/onPause/onDestroy/render/preheat/loadLocalUrl/softReload/refresh/
  看门狗探针/热状态同步/视口重应用/缩放与 UA 设置全部改走它。
  返回 true 之后不存在任何对旧实例的调用路径。
- setupWebView() 会被恢复流程再跑一遍 → 热状态订阅加 thermalSubscribed 幂等守卫，
  避免重复 collect 造成重复降级注入。

二、异步初始化 WebView（第二优先级）
- 新增 web/WebViewStartup：androidx.webkit WebViewCompat.startUpWebView +
  单线程后台执行器，把 Chromium provider 首次初始化（ColorOS 实测 600~900ms）
  从主线程挪走；回调记录 totalTimeInUiThreadMillis 进 engine.log 供对照。
- DshApp.onCreate() 末尾调用，之后到 onCreate 结束前不触碰任何 WebView API
  （否则初始化会被拉回主线程同步等待，异步白做）。
- 依赖 androidx.webkit:webkit:1.14.0（1.16.0 带 kotlin-stdlib 2.1.20 元数据，
  与本项目 Kotlin 1.9 编译器不兼容，构建期即失败；1.14.0 无此冲突且已含
  startUpWebView）。
- 能力不支持时静默降级（runCatching + done=true），不影响功能。

三、本地资源直供（第二优先级）
- 保留原设计：CSS / 字体 / 图片 / 媒体拦截（不经 V8，无 code cache 可失）。
- shouldInterceptRequest 是 IO 线程同步执行，为它加了显式约束注释，
  并把 JS 拦截做成显式开关 INTERCEPT_JS（默认 false）。
  原因：一旦返回自有响应，该 JS 就脱离 Chromium HTTP cache 与 V8 code cache，
  1MB 级 bundle 每次导航都要重新解析+编译（几十~上百毫秒），抵消拦截省下的
  一次 Node/proot 往返。开关保留，便于真机 A/B。

四、高频事件合帧注入（第三优先级，前端不可改的补救）
- 新增 web/EventCoalesce：注入幂等脚本，包装 EventTarget.prototype.addEventListener，
  对 scroll/resize/touchmove/pointermove/mousemove/wheel 用 requestAnimationFrame 合帧，
  同一帧内多次触发只执行最后一次；保留 removeEventListener 配对（wrapper 反查）、
  非目标事件零影响、空闲零开销。
- Native 侧 in-flight 守卫：AtomicBoolean gate + pending，最多一次在飞，
  合并期间的新请求落地后补一次，不堆 IPC。
- 只对引擎页注入，预览页（第三方内容）不动。
- 本机 node 复刻验证：3 次同帧 scroll → 只执行 1 次（最后一次）；跨帧各执行 1 次；
  remove 后不再触发；click 保持同步。

五、明确跳过：WebView 复用池
- 复用前提是「同容器、同账号、同 origin 的静态页」。本项目是单容器单 origin SPA，
  页面里存在登录/支付/支付回跳等有状态流程；loadUrl("about:blank") 清空上下文是
  异步的，归还即可复用无法保证隔离，且 about:blank 往返本身有成本。
- 在这套结构下拿不到可测量的收益，风险（会话串页、输入残留）却真实存在 → 不做。
  已用「退役 + 前台静默重建」覆盖它想解决的场景（渲染层坏掉后有一个干净的新实例）。

六、验证方式（本环境无真机，以下为可用命令）
- chrome://inspect：看注入是否只执行一次、Long Task 是否消失、Scroll 期间
  Rendering 面板掉帧是否改善。
- adb shell dumpsys gfxinfo app.dsh.mobile.dev framestats：对比滚动时
  单帧 16.6ms 预算的越界帧比例。
- engine.log 新增一行 perf: webview startup <in-flight|done in Xms> · coalesce installs=N ·
  thermal ...，启动后即可确认三项优化是否生效。
- 复现自愈：后台挂 30 分钟（ColorOS 省电策略下必然回收渲染器），切回前台应看到
  一次静默恢复（日志 webview recovered (foreground after renderer reclaim)），
  且**只有一次**，不再循环。

本地资源热优化（v1.6.36）

主题：用 mmap 直读绕开慢路径，把解码移出热受限窗口，降频时串行 IO + 暂停非核心解码。

本次优化（v1.6.31）

主题：解码与填充率预算 —— UI 资源加载不再在主线程解大图，模糊不再逐档抢主线程。

问题现象
- 从任意页面切回设置体系（设置主页/外观/背景图/状态栏定制）时先顿一下；
  拖动「模糊强度」滑块卡成幻灯片；点进外观页有可见延迟。
- 宠物/状态窗拖拽已由 v1.6.30 的 RenderBudget 兜住，但只要设置页在解码或卷积，
  主线程照样被占住 —— 也就是「UI 局部更新把场景渲染拖垮」。

根因
1. ThemedActivity.applySettingsBackground() 在 setContentView 与每次 onResume 里
   同步执行「decodeFile + 最长边 1080 的真高斯模糊 + 全树压暗卡片」。
   缓存命中时也要解一张 1080 宽 PNG（≈4 MB）；未命中时是几百毫秒级逐像素卷积。
   每个设置页都是新 Activity，等于「切一页解一次、算一次」。
2. SettingsBgActivity 拖动滑块每移动一档就 refreshPreview() + applySettingsBackground()，
   一次拖动 = 二十几次主线程卷积（480 宽预览 + 1080 宽整页各一遍）。
3. AppearanceActivity.refreshImageRows() 为 56dp 的缩略图同步解码 1440×1080 原图
   （6.2 MB 分配），解码量与真正要画的像素差一个数量级。
4. ExpandedStatusBarActivity.render() 每次 onResume 都解整张背景、逐张解贴纸，
   并 removeAllViews() 重建全部贴纸（每次重建都触发一轮 measure/layout）。
5. ImageFx.cachedBlur() 解析相原图时先 decodeFile 全尺寸，再 limitEdge 缩小 ——
   4000×3000 就是先分配 48 MB 再扔掉 90%。

改动
1. 新增 ui/ImagePipeline.kt：进程级图片解码流水线。
   · 单线程后台 worker（img-decode，优先级 NORM-1），串行限流，最多占一个核
   · 按 tag 覆盖：同一控件连续请求只保留最新一条，队列里不堆同 tag 多份
   · 按显示尺寸采样解码（只取 2 的幂、不放大；宽高都够大才继续降）
   · 内存 LRU 按 byteCount 记账（堆上限 1/8），键含 mtime+length，换图即失效
   · 结果经 RenderBudget.postOnce 合帧交付：同一 tag 一帧内只 apply 一次
   · 过期丢弃：算完发现 tag 最新键已变就扔（stale 计数），不拿旧图盖新图
   · cancel(tag) / clearCache() / stats() / dump()（统计全是实测值）
2. ThemedActivity：背景改走 ImagePipeline；位图键与交付键分离（改 alpha 不重算模糊）；
   参数未变直接短路返回，连一个 View 都不碰；卡片压暗用 cardsDimmed 门控只做一次；
   onDestroy 撤销在途请求。
3. SettingsBgActivity：预览改走 ImagePipeline（后台 + 合帧 + 去重）；
   滑块拖动中不再重贴整页背景，改到 onStopTrackingTouch（SimpleSeek.stopped()）。
4. AppearanceActivity：缩略图按 168dp 采样异步解码（THUMB_TAG，onDestroy 撤销）。
5. ExpandedStatusBarActivity：背景与贴纸都按预览实际尺寸异步解码；

6. ImageFx：源图解码收敛为 decodeForBlur()（inJustDecodeBounds + inSampleSize），
   最终尺寸不变、观感不变；MAX_EDGE 提升为公开的 MAIN_EDGE，与调用方同一口径。

本次修复（v1.6.30）

主题：帧预算与资源隔离 —— 叠加窗口的帧驱动不再各自 postDelayed 抢主线程。

问题现象
- 拖动宠物/状态悬浮窗时「跟手发涩」，松手吸附到位那一下会顿一下；同一进程里
  WebView 正在流式输出时更明显。

根因
1. 进程内有多条互不相识的帧驱动：宠物漫游 32ms、宠物甩抛 16ms、状态窗吸附 16ms、
   两个窗口的拖拽（每收到一个 MotionEvent 就发一次 WindowManager.updateViewLayout）。
   它们各自 postDelayed 自排下一拍，彼此不知道，谁跑了多久、这一帧还剩多少预算都没人管。
2. postDelayed(16) 与真实帧间隔不同步（16.67@60 / 11.1@90 / 8.3@120Hz），
   会周期性「丢一帧 / 补两帧」。v1.6.21 已在宠物 move 驱动上踩过，其它路径未改。
3. 拖拽的窗口事务次数与**触摸采样率**同阶（120/240Hz），而不是与刷新率同阶 ——
   每帧内多出来的几次 binder IPC 进 system_server / SurfaceFlinger 纯属白烧，
   并且与 WebView 自己的合成抢同一侧资源。

改动
1. 新增 ui/RenderBudget.kt：进程级帧预算调度器。
   · 单一 Choreographer 调度源；无订阅者时完全停摆（不是空转 60fps）
   · 每帧主线程预算（默认 5ms ≈ 30% 帧时间），超预算把 NORMAL/LOW 顺延到下一帧
     （顺延不是丢弃），HIGH 永远不受限
   · 按 (优先级, 注册序) 稳定排序分发
   · 帧间隔 EMA 卡顿检测：连续卡顿把 LOW 订阅降频（间隔 ×2），顺畅后恢复
   · 保活回退：息屏/doze 下 Choreographer 不送帧时用定时器顶上，保持旧语义
   · postOnce：同一 id 一帧内多次请求合并，后写覆盖先写
   · stats()/dump() 暴露实测值（帧数、均值/峰值分发耗时、顺延次数、是否降频）
2. PetOverlayService：拖拽改 postOnce 合帧（每帧最多一次窗口事务）；
   甩抛交给调度器（仍 16ms，物理步长恒 1/60）；stopFling/onDestroy 撤销订阅。
3. StatusOverlay：拖拽同样合帧；吸附动画改为 vsync 排帧；hide() 撤销订阅。

验证
- 新增 scripts/probes/_test_render_budget.py 45/45
- 模型算术（60Hz 帧 / 240Hz 触摸 / 1 秒）：窗口事务 575→150 次/秒、
  单帧峰值 11→3 次。⚠ 这是算术复刻，不是真机测量。
- 真机需 dumpsys gfxinfo app.dsh.mobile.dev framestats 复核。

本次修复（v1.6.18）

问题现象
- 使用「设置 → 维护与高级 → 删除对话」删除对话后，引擎重启会报：
  typert gateway: directoryPicker/list: active Service "directoryPickerController" is unavailable
  同时提示「部分插件加载失败」。正常使用（不删除对话）不出现。

根因
1. 删除流程会改写 DSH_HOME/storages/workspace.json。引擎启动时用 zod schema
   严格校验该文件的不变量：
     · 每个 sessionId 只能归属一个工作区且不重复
     · global.archivedSessionIds / pinnedSessionIds 必须仍存在于某个工作区的 sessionIds
     · global.workspaceIds 必须与 tables.workspaces 一致
     · defaultWorkspaceId 不能指向已不存在的工作区
   删除会话后这些引用可能悬空，workspace 域加载即失败。
2. workspace-controller 激活依赖该域（static inject = ["directoryPicker", ...]），
   它同时也是 directoryPickerController 服务的提供者。域失败 → controller 不激活
   → 网关按 descriptor.service 取不到该服务，抛出上述错误。
3. 删除后的重启本应跳过「插件快速启动」，但 requestSkipNext 使用
   SharedPreferences.apply()（异步落盘），restart() 随即在同进程内 consume，
   存在竞态，导致仍走 hold 路径：第三方插件被临时摘除、靠 HMR 补加载，
   表现为「部分插件加载失败」。

修复
- 新增 WorkspaceRegistryHealer：幂等收敛 workspace.json 不变量（备份 + 原子写，
  无脏数据时不写文件）。
- ChatWiper 删除/清空流程结束后立即调用该自愈器，确保重启前注册表自洽。
- EngineSupervisor 启动时（ensureUserDataExternal 之后）再兜底自愈一次，
  让已经写坏的老数据在升级后首次启动即可恢复。
- PluginFastBoot.requestSkipNext / consumeSkipNext 改用 commit() 同步落盘，
  保证「删除后完整加载」一定生效。
